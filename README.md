# Factura Shop

Магазин изделий ручной работы: `/` — витрина, `/admin/` — отдельная панель, `/api/` — Hono/tRPC API. React/Vite, Node.js 22.12+, npm, MySQL 8 или SQLite. Цены хранятся в целых рублях.

## Установка

```sh
npm ci --prefix app
npm ci --prefix admin
cd app
```

Для локальной разработки скопируйте `.env.dev.example` в `.env`, заполните Telegram-настройки. Для production используйте `.env.example`. Реальные `.env`, базы, загруженные файлы и логи исключены из Git. Зависимости зафиксированы отдельным `package-lock.json` в каждом приложении.

```sh
npm run db:migrate
npm run seed
npm run dev:all
```

Витрина: `http://localhost:3000`, панель: `http://localhost:3001/admin/`. Vite слушает локальный интерфейс. `DEV_ADMIN_ORIGIN=http://localhost:3001` разрешает изменения через локальную панель; в production эта переменная запрещена. Вход без Telegram, тестовые пользователи и пароль по умолчанию отсутствуют.

## Telegram и права

Используется существующий legacy Login Widget с HMAC-SHA256, а не OIDC или Mini Apps initData. Настройте домен бота через BotFather для [legacy widget](https://core.telegram.org/widgets/login-legacy). Бот должен поддерживать этот режим; настройка нового OIDC-клиента сама по себе его не включает. Если Telegram перестанет поддерживать legacy widget для вашего бота, потребуется отдельная миграция протокола.

- `TELEGRAM_BOT_TOKEN` — токен бота, только на сервере.
- `TELEGRAM_BOT_NAME` — username бота без `@`.
- `SUPER_ADMIN_TELEGRAM_ID` — положительный безопасный целочисленный ID владельца.
- `PUBLIC_ORIGIN` — точный публичный origin, например `https://shop.example.com`, без завершающего `/`.
- `APP_SECRET` — случайная строка от 32 символов. Генерация: `node -e "process.stdout.write(require('crypto').randomBytes(48).toString('hex'))"`.

Миграция и seed идемпотентно создают владельца из окружения даже при непустом списке. Случайный посетитель прав не получает. Другие ID добавляются владельцем на странице «Доступ». Роли: `admin` управляет каталогом, текстами, заказами и изображениями; `super_admin` дополнительно управляет допуском и видит журнал. Права владельца нельзя изменить ни одним API-методом управления доступом.

Роль и активность перечитываются на сервере при запросах. Изменения списка допуска выполняются в транзакции с блокировкой записи владельца; все ранее выданные сессии целевого пользователя удаляются. Реактивация требует нового входа. Подписанный Telegram-пакет можно использовать один раз; допускается возраст до часа и сдвиг часов в будущее до 30 секунд. Сервер и БД должны иметь синхронизированное время.

Cookie `factura_admin_sid`: HttpOnly, SameSite=Lax, Secure в production, срок 8 часов. В БД хранится хеш случайного токена. Выход удаляет серверную сессию. Смена APP_SECRET аннулирует все ранее выданные сессии. Изменяющие запросы требуют разрешённый Origin; reverse proxy должен сохранять Origin и Cookie и не разрешать CORS со сторонних сайтов. Перезапуск приложения не восстанавливает отозванные сессии. Содержимое audit log и контакты покупателей доступны только соответствующим ролям; определите сроки хранения и резервного копирования.

Для восстановления владельца остановите приложение, сделайте резервную копию БД, задайте проверенный `SUPER_ADMIN_TELEGRAM_ID`, повторите `npm run db:migrate`, удалите действующие сессии административной командой БД и перезапустите сервер. Смена владельца через интерфейс не предусмотрена. Проверьте и отзовите лишние старые записи допуска после восстановления.

## Конструктор страницы

Главная страница собирается из блоков, которыми администратор управляет на странице «Конструктор» (`/admin/builder`): добавляет из библиотеки, переставляет перетаскиванием, скрывает, редактирует и удаляет. Библиотека: обложка, текстовый блок, плитка преимуществ, галерея, одиночное изображение, видео (YouTube/Vimeo), FAQ, этапы, а также разделы «О мастерской», «Каталог», «Товары» и «Доставка». Блоки «Каталог» и «Товары» показывают данные коллекций и товаров и существуют в единственном экземпляре; порядок блоков сохраняется транзакцией с проверкой состава.

Данные блоков хранятся в таблице `blocks` (JSON с серверной Zod-валидацией по типу, лимит 60 блоков). У каждого блока можно задать собственный HEX-цвет фона (миграция `003_blocks_background`); цвет текста секции подбирается по яркости фона, а самодостаточные элементы (карточки товаров, плитки, вкладки) сохраняют свои цвета. Миграция `002_blocks` создаёт таблицу, стартовый набор блоков формируется из текущих текстов `siteContent` при миграции или seed и идемпотентен. Шапка (название магазина), футер и контакты остаются на странице «Тексты и контакты»; навигация шапки строится из присутствующих блоков и на узких экранах сворачивается в бургер-меню. Видеоблок принимает только HTTPS-ссылки YouTube/Vimeo, ссылки кнопок — якоря, локальные пути или HTTPS.

## Заказы и изображения

Корзина отправляет имя, контакт, комментарий, ID товаров и количества. Сервер сверяет активные товары и пересчитывает сумму. Наличие и доставка подтверждаются отдельно; автоматическая оплата не реализована. Заказ появляется в разделе «Заказы» и счётчике новых заказов в навигации панели (обновление каждые 15 секунд); клиент видит номер и подтверждённую сервером сумму. Внешняя рассылка уведомлений не настроена.

`POST /api/upload` доступен только администраторам. До 5 МБ, JPEG/PNG/WebP по фактическому декодированному формату, до 16 млн пикселей. Изображение перекодируется в WebP до 2400×2400, метаданные удаляются. SVG, исполняемые и повреждённые файлы отклоняются. `UPLOAD_DIR` в production обязателен и указывает абсолютным путём на постоянный каталог вне `dist`, с правами записи только у сервиса; резервируйте его вместе с БД. Не храните секретные материалы в публичных изображениях. Загруженные изображения доступны по `/uploads/<uuid>.webp`.

Публичный API ограничивает размер тела до 6 МБ и частоту запросов через БД: 300 запросов/минуту на прямой сетевой адрес, 10 для входа и заказов. За reverse proxy адрес может быть общим для посетителей: дополнительно настройте лимиты на прокси по реальному IP, разрешив доверенные заголовки только от вашего прокси. Приложение не доверяет произвольному X-Forwarded-For. Один процесс обслуживает SQLite; для нескольких процессов используйте MySQL и общий каталог изображений.

## Миграции и данные

```sh
npm run db:migrate
```

Версионируемые SQL-файлы: `app/db/migrations/001_initial.*.sql` и `002_blocks.*.sql` для каждого диалекта. Команда применяет SQL по порядку и сохраняет имя и контрольную сумму в `schemaMigrations`; повторный запуск пропускает применённые файлы, изменение уже применённого файла отклоняется. SQLite — транзакционно, MySQL DDL — с неявным commit. Исходная миграция содержит безопасные `CREATE IF NOT EXISTS`, поэтому частичный запуск MySQL можно повторить. Не запускайте два процесса миграции одновременно. Данные не удаляются, старые OAuth-таблицы существующей базы оставляются нетронутыми. Деструктивный старый скрипт удалён. `seed` — необязательное демонстрационное наполнение пустого магазина; не содержит учётных данных.

Перед обновлением существующей БД сделайте резервную копию и проверьте схему и данные на копии. `CREATE IF NOT EXISTS` не исправляет несовместимые старые столбцы и не добавляет FK/индексы в существующие таблицы. Для такой базы нужна отдельная проверенная ALTER-миграция после проверки отсутствия товаров с несуществующими коллекциями. На новых БД связь товаров с коллекциями защищена FK; приложение проверяет связность и запрещает удалять непустую коллекцию. Новые изменения схемы добавляйте отдельными SQL-миграциями для обоих диалектов, не изменяя данные вручную на работающем сервере.

## Проверки

```sh
npm run lint
npm run format:check
npm run check
npm test
npm run build
npm run test:deployment
cd ../admin
npm run lint
npm run format:check
npm run check
```

`app` build собирает витрину, отдельную панель и API. Тесты используют чистую SQLite в памяти; проверяют подписи, сроки, повторы входа, роли, защищённого владельца, конкурирующие изменения, отзыв сессий, CSRF, расчёт заказов, ограничения запросов и загрузку изображений. GitHub Actions также проверяет MySQL на чистой базе. Статические проверки и тестовые HMAC-пакеты не заменяют проверку входа с реальным ботом на HTTPS-домене.

## Развёртывание

На Ubuntu/Debian используйте интерактивный мастер: `sudo bash deployment/setup.sh`. Он спрашивает разрешение на установку компонентов (git, Node.js 22, MySQL, nginx), задаёт вопросы о конфигурации (диалект БД, Telegram-бот, владелец, origin), генерирует `APP_SECRET`, клонирует выбранный тег в `/opt/factura/current`, собирает проект, применяет миграции, устанавливает `factura.service` и (опционально) механизм обновления из панели. Ручная установка:

1. Установите зависимости через `npm ci` для обоих приложений, выполните проверки и `npm run build` из `app`.
2. Настройте MySQL/SQLite и серверный `.env`. В production обязательны HTTPS `PUBLIC_ORIGIN`, Telegram-конфигурация, ID владельца, секрет и абсолютный `UPLOAD_DIR`; `DATABASE_URL` обязателен для MySQL. Установите `NODE_ENV=production` в окружении сервиса. Примерные значения конфигурации нельзя использовать как реальные секреты.
3. Выполните миграцию; при первом запуске при необходимости выполните `seed` и замените демонстрационные контакты и тексты.
4. Запустите `npm start` из каталога `app`. API слушает `HOST=127.0.0.1`, `PORT=3000` по умолчанию. Сохраните каталог `db/migrations` для команд миграции; запуск собранного сервера не требует `tsx`.
5. Reverse proxy завершает TLS и направляет `/`, `/admin/`, `/api/`, `/uploads/` одному сервису. Ограничьте тела до 6 МБ, настройте лимиты, HTTPS и HSTS; не публикуйте Node-порт напрямую. Не включайте `Cross-Origin-Opener-Policy: same-origin`, мешающий Telegram popup.
6. На чистой базе проверьте вход владельца и разрешённого администратора, отказ чужому ID, отзыв доступа, реальный заказ и загрузку фото, затем резервное копирование и восстановление.

Production-развёртывание и отправка в GitHub автоматически не выполняются. Исходный аудит сохранён в `docs/factura-shop-audit.md`; проверенные выводы и результаты запуска — в `docs/implementation-report.md`.

## Релизы и обновление сервера

Версия задаётся файлом `VERSION` в корне и `CHANGELOG.md`. Push тега `v*` запускает workflow `Release`: он сверяет тег с `VERSION`, прогоняет проверки и публикует GitHub Release с заметками из CHANGELOG. Репозиторий приватный, поэтому серверу нужен fine-grained PAT (Contents: Read-only, Metadata: Read-only) в `GITHUB_TOKEN` — это единственная переменная с учётными данными GitHub (API и HTTPS git); переменные `SERVER_UPDATE_*` задают только конфигурацию механизма обновления. Для публичного репозитория `GITHUB_TOKEN` можно оставить пустым.

Обновление до последнего релиза доступно super_admin на странице «Обновление сервера» (`/admin/server-update`): панель показывает текущую версию, последний релиз, этапы выполняющейся операции и результат последней операции, кнопка запускает на сервере `deployment/factura-update.sh` через ограниченную sudoers-запись (`SERVER_UPDATE_ENABLED=true` включает механизм; установка — через `deployment/setup.sh`). Скрипт под блокировкой `flock` переносит себя в transient unit systemd (обновление не прерывается перезапуском сервиса), определяет корень установки (`/opt/factura/current` или `/opt/factura`, нестандартная раскладка — через root-конфиг `/etc/factura/update.env`), проверяет чистоту рабочего дерева и доступ к GitHub, создаёт резервную копию БД и `.env` в `/var/backups/factura`, выполняет `git checkout` тега от имени владельца репозитория, `npm ci`, сборку, миграции, переустанавливает себя, systemd-юнит и sudoers из архива нового тега, скачанного с GitHub (доверенный источник, не рабочее дерево), перезапускает `factura.service` и делает healthcheck; при сбое код и файлы деплоя откатываются на предыдущие и сервис перезапускается. База данных не откатывается — восстановление из резервной копии выполняется вручную. Git-доступ: HTTPS c `GITHUB_TOKEN` либо SSH deploy key (`core.sshCommand` в конфигурации репозитория, настраивается `setup.sh`). Журнал: `/var/log/factura/update.log`, статус: `SERVER_UPDATE_STATUS_PATH`. Команда обновления пишется в журнал доступа. Обновление до произвольного тега из панели не предусмотрено, только последний релиз; конкретный тег — вручную `sudo /usr/local/sbin/factura-update.sh` после `git checkout`. Одноразовый переход сервера со старого механизма (v0.1.x) описан в `docs/server-update-migration.md`.
