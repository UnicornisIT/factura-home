# Проверка аудита Factura Home

**Дата:** 17 ноября 2026 г.

**Объект:** GitHub `main`, Factura Home 0.5.0, SHA `18f7eba1922eb85f1356e78524e1d8fc01d1e9ee`. [Коммит](https://github.com/UnicornisIT/factura-home/commit/18f7eba1922eb85f1356e78524e1d8fc01d1e9ee).

Локальная ветка `main` указывает на 0.2.4 (`17eb1ac9475573dac63f5fa2ddb9e418f4f388c8`). Локальный `origin/main` совпадает с тегом `v0.5.0` (`89d3562cd8cfce70218c8edf44ac15a7eed22dba`). GitHub Compare показал один изменённый файл между релизом и целевым SHA, `app/tests/telegram-auth.test.ts`. Для проверки распакован архив релиза, в тест внесён точный diff из `main`. Рабочая ветка при этом осталась `fix/server-update-reliability`. [Сравнение SHA](https://github.com/UnicornisIT/factura-home/compare/89d3562cd8cfce70218c8edf44ac15a7eed22dba...18f7eba1922eb85f1356e78524e1d8fc01d1e9ee).

Приложенный аудит содержит **94 отдельных ID**: 13 в разделе P1 и 81 в разделе P2. Статус ниже присвоен каждому ID. Итог: 20 CONFIRMED, 35 PARTIALLY CONFIRMED, 37 FALSE POSITIVE, 2 NEEDS REPRODUCTION, 0 ALREADY FIXED. CONFIRMED и PARTIALLY CONFIRMED обозначают доказуемое по коду поведение либо воспроизведённый результат. Для проверки среды и сценариев, в которых статического анализа недостаточно, указан NEEDS REPRODUCTION. Пути и строки относятся к проверенному SHA. В таблицах стрелка показывает путь до затронутого слоя.

## Дополнительная проверка путей

- **Telegram, сессии и права.** Подписанный виджетом payload → strict Zod и HMAC/date → активный allowlist → replay registry, выпуск случайного opaque token и audit в одной транзакции → HttpOnly/Secure/Lax cookie в production. На следующих запросах `context.ts:22–39` читает текущую роль из БД, а revoke удаляет сессии. Роль из cookie не принимается. Disable и logout прекращают последующий доступ. Успевший пройти role middleware запрос следует анализировать отдельно от новых запросов после revoke.
- **CSRF, upload и XSS.** POST требует точный Origin. Upload дополнительно проверяет сессию и роль, размер запроса/файла, преобразует формат через Sharp, пишет WebP под случайным именем. `boot.ts:69–205` ограничивает ожидание нативной обработки, которая может завершиться после таймаута. Ошибка аудита после удачного upload уже обработана локально, в отличие от обычных TRPC мутаций. Чтение uploads ограничено именами файлов заданной формы.
- **Checkout и Telegram.** Заявленная клиентом цена не используется. DTO проверяет количество, сервер читает товары, рассчитывает total, сохраняет order + outbox в одной транзакции. UNIQUE requestKey и повтор lookup защищают от дубликатов одного заказа с UUID. Право получателя и идентификатор подписки проверяются ещё раз при доставке. Повторы после неопределённого результата Telegram описаны в N-3.
- **Черновики.** Builder отправляет version и снимок. `queries/blocks.ts:136–163,215–290,342–391` блокирует singleton (MySQL FOR UPDATE/SQLite write transaction), отклоняет устаревшую version, валидирует блоки, обновляет публикацию и ссылки меню атомарно. Restore возвращает текущую публикацию, а не произвольную историческую версию. Отдельное восстановление повреждённого сериализованного draft требуется по BE-8.
- **Витрина и мобильные экраны.** По разметке у mobile menu есть aria-expanded, controls и Escape, у корзины другой lifecycle (FE-21). Геометрия, zoom, touch targets, overflow, экранные читалки и Playwright/браузерная матрица требуют динамической проверки.
- **N-6 (P3, CONFIRMED).** app/db/migrate.ts:21–29 хеширует текст SQL с рабочими окончаниями строк. Одна и та же 004 имеет разные SHA-256 в Windows CRLF и LF архиве. Если применить Windows копию и затем подключить Linux migrator к той же БД, ожидается пропуск неизменённой SQL-миграции, фактически checker выдаёт Applied migration was modified. Зафиксировать LF для SQL-файлов и предусмотреть совместимую сверку старых checksum. Проверить общую БД после переноса между средами.
- **N-5 (P3, NEEDS REPRODUCTION).** `ServerUpdate.tsx:35–75`: перезагрузить UI между принятием запуска и первым статусом running. React state `awaitingResult` сбрасывается, поэтому если статус ещё старый, polling может остановиться. Ожидается сопровождение launch после reload, проверить задержанный статус и использовать возвращаемый operation ID или короткий polling grace period.
- **N-7 (P3, CONFIRMED).** app/tests/production.test.ts:17–23,38–56 считает отказом конфигурации любой status, отличный от 0. При timeout или ошибке spawn Node возвращает status null, и негативный тест может пройти без валидации. Ожидается контролируемый ненулевой exit и конкретная ошибка конфигурации. Проверить result.error, signal, числовой exit code и ожидаемый диагностический код для каждого случая.
- **N-8 (P3, CONFIRMED).** app/tests/deployment-smoke.ts:14,54–66 использует фиксированный 3199. При двух параллельных запусках один сервер получает EADDRINUSE. Это воспроизвелось при перекрытии первичного запуска и повтора. Ожидается независимость smoke-процессов. Использовать отдельный динамический порт с передачей от запущенного дочернего процесса.
- **Исторический аудит.** Подтверждены наличие server-side расчёта, проверки ролей на upload, production исключения dev login, Origin и cookie flags, запрета изменения owner через allowlist, аудит-лога и production error mask. Это проверка указанных механизмов на целевом SHA; надёжность аудита при сбое рассмотрена в BE-1.

## Команды и результаты

Запуски выполнялись на Windows с Node 22.23.4 и локальными зависимостями. Оба lockfile совпадают с lockfile исходной рабочей копии, откуда зависимости скопированы. Первичная попытка чистой установки offline под системным Node 26 завершилась EPERM. Нативный better-sqlite3 установлен для Node 22. Проверки используют синтетические реквизиты и временные SQLite. Live Telegram, production, внешняя БД и системный updater не использовались.
