# Отчёт: инцидент с загрузкой фотографий и улучшения надёжности

Дата: 2026-11-10
Версия на сервере: v0.2.3
Ветка: `fix/upload-reliability`

---

## 1. Причина инцидента — подтверждена

Симптом: в админ-панели при редактировании коллекции кнопка «Загрузить фото» зависала в состоянии «Загрузка…», изображение не появлялось.

Диагностика на сервере и на рабочем месте администратора установила:

- nginx возвращал **HTTP 408** на `POST /api/upload`;
- каталог `/var/lib/factura/uploads` доступен для записи, место на диске есть;
- локальный multipart-запрос через nginx на сервере — **401 за 0,064 с** (сервер здоров);
- запрос с Windows через `curl --noproxy "*"` — **401 за 2,48 с** (сеть и nginx работают);
- **после отключения системного прокси на Windows фотографии успешно загружаются и сохраняются через админ-панель**.

**Первопричина: системный сетевой прокси на Windows-машине администратора**, через который multipart-запрос не доставлялся корректно (nginx фиксировал 408 — истечение ожидания тела запроса). Серверный обработчик `/api/upload` ошибки не содержал — это подтверждено и локальным сквозным воспроизведением production-сборки (вход через Telegram → загрузка с Content-Length и chunked → ~150–650 мс → файл доступен по `GET /uploads/:name`).

Изменения в этой ветке — **улучшения надёжности (hardening), а не исправление первопричины**. Они устраняют реальные дефекты, из-за которых любой внешний сбой сети/прокси/сервера превращался в необратимое зависание интерфейса и был недиагностируем:

1. **Клиент: `fetch` без тайм-аута** — при любом транспортном сбое (как в этом инциденте) кнопка оставалась в «Загрузка…» навсегда, пользователь не получал ни ошибки, ни возможности повторить.
2. **Сервер: `audit()` после `writeFile()` без изоляции** — при сбое журнала файл уже сохранён, но клиент получал 500 без URL.
3. **Сервер: отсутствие тайм-аута у Sharp/libvips** — гипотетическое зависание нативного декодера подвешивало HTTP-запрос навсегда.
4. **Сервер: нулевое логирование этапов** — место сбоя на production было невозможно определить (в этом инциденте диагностику пришлось собирать вручную).

## 3. Содержание изменений и обоснование решений

### Клиент (`ImageUpload.tsx`)

- **Тайм-аут 60 с (`AbortController`).** Именно то, чего не хватило в инциденте: вместо вечного «Загрузка…» администратор через минуту получил бы понятное сообщение и возможность повторить. Отмена корректно обрабатывается, `busy` сбрасывается всегда (успех/ошибка/отмена/размонтирование).
- **Одна загрузка за раз** — повторный выбор файла во время активного запроса игнорируется.
- **Валидация ответа** — загрузка успешна только при `{ url: string }` с локальным путём; пустой/битый ответ прокси больше не сможет «молча пройти».
- **Сообщения об ошибках**: тайм-аут, сеть, 401/403/413/429/5xx, короткое безопасное сообщение сервера. Без stack trace, путей и секретов.
- **`onBusyChange`** — формы коллекций и товаров блокируют «Сохранить» до завершения загрузки (URL не теряется).

### Сервер (`POST /api/upload`)

- **Этапная изоляция ошибок** с кодами по спецификации: parse-body сбой → 400; >5 МБ → 413 (ранее 400, приведено к п.10 ТЗ); отказ формата → 400; запись ФС → 500; без сессии → 401; роль/Origin → 403; rate limit → 429.
- **Тайм-аут Sharp 15 с — оставлен осознанно.** `Promise.race` не отменяет нативную операцию libvips: после ответа она доживает в пуле потоков, удерживая память в пределах входного буфера (≤5 МБ, `limitInputPixels=16M`). Альтернатива — навсегда занятые HTTP-соединение и поток. Штатная обработка занимает <1 с, тайм-аут срабатывает только на патологических данных. Компромисс зафиксирован комментарием в коде.
- **Сбой `audit()` после записи файла — оставлен осознанно.** Файл уже сохранён; вернуть 500 — значит потерять URL при успешной операции (дефект №2). Потеря события аудита **не бывает незаметной**: ошибка пишется на уровне `error` (stderr → journalctl) с этапом и причиной, а успешная загрузка — отдельной записью `Upload completed`. Идентификатор пользователя в лог не дублируется намеренно (scrubber всё равно заменяет ключи, содержащие `telegram`, на `<redacted>`); событие сопоставляется по времени с записью аудита/загрузки.
- **Логирование этапов** — `stage` + категория ошибки (`EACCES`/`EROFS`/`ENOSPC`, `Error.name`) + размер + длительность; без токенов, cookie, путей и содержимого файлов. В следующем инциденте слой сбоя будет виден в `journalctl` сразу.
- **Избыточных изменений нет**: проверки формата/размера/авторизации/Origin/rate limit не ослаблены и не дублированы; новые сущности (`withTimeout`, `OperationTimeoutError`, тестовый хук тайм-аута) минимальны и покрыты тестами.

### Ранее существовавшая проблема тестов (не связана с изменениями)

`app/tests/production.test.ts` при полном параллельном прогоне на медленной машине может падать: дочерний процесс `spawnSync(node --import tsx …, timeout: 30000)` не укладывается в собственный 30-с тайм-аут под нагрузкой (`expected null to be +0`). Изолированно файл проходит (~13 с). Тест проверяет `api/router.ts`/`api/lib/cookies.ts` и не затрагивает изменённый код. В CI (Linux) не воспроизводился. Рекомендуется отдельно поднять `timeout` у `run()` в этом файле — в эту ветку изменение не включено, чтобы не смешивать несвязанные правки.

## 6. nginx / systemd — корректировки не требуются

Проверено по факту инцидента:

- `client_max_body_size 6m` соответствует `bodyLimit` приложения;
- стандартные `proxy_read_timeout` (60 с) достаточны: сервер отвечает за ≤15 с даже при зависшем декодере;
- `Origin` доходит до node, `PUBLIC_ORIGIN` совпадает (403 не возникал);
- `ReadWritePaths=/var/lib/factura …` в порядке, запись в uploads подтверждена.

Изменять конфигурацию не нужно.

## 7. Развёртывание

Не требуется для устранения инцидента (причина — на стороне клиента). Ветка `fix/upload-reliability` предназначена для штатного ревью и слияния в `main`; деплой на `/opt/factura` — общим порядком после релиза (панель «Обновление сервера» или `git checkout <тег> && npm ci && npm run build && systemctl restart factura`). Миграций БД нет, откат — checkout предыдущего тега и пересборка.

Рекомендация администратору панели: не отключать системный прокси глобально, а добавить домен магазина в исключения прокси (bypass list), либо отключить прокси для локальных/доверенных адресов.

## 8. Статус и оставшиеся риски

- **Первопричина инцидента (прокси Windows) изменениями в этой ветке не устраняется и не может устраняться** — она на стороне клиентской сети. Ветка делает поведение при таких сбоях предсказуемым: тайм-аут, понятная ошибка, повторная попытка, логи этапов на сервере.
- Оставшиеся риски:
  - тайм-аут Sharp оставляет доживающую нативную операцию (память ограничена 5 МБ входа / 16 Мп; см. комментарий в коде);
  - сбой `audit()` при успешно записанном файле оставляет событие только в error-логе (см. обоснование в §3);
  - `production.test.ts` остается чувствительным к нагрузке машины (существующая проблема, §4).
