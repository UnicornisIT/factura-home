# Глиняная мастерская — аудит исходников перед GitHub и деплоем

> Исторический аудит до исправлений. Текущее состояние описано в [отчёте](implementation-report.md). Название удалённой OAuth-интеграции заменено нейтральным обозначением.

Дата: 2026-11-08. Источник: `factura-shop-telegram-admin.zip` (архив, предоставленный владельцем проекта).

> Проверка статическая: просмотр структуры, серверного API, интерфейсов и тестовых сценариев. Тесты и production-сборка НЕ запускались: в архиве нет `node_modules` и lock-файлов зависимостей. Отсутствие найденной проблемы не означает доказанной безопасности.

## Итог

- Структура: `app/` (витрина + Hono/tRPC API) и `admin/` (отдельное React/Vite SPA). Админка открывается на `/admin/` того же сервера в production, на `localhost:3001` в dev.
- Telegram Login Widget, серверная HMAC-проверка, allowlist по Telegram ID, роли `super_admin` и `admin` уже реализованы.
- Первый super_admin **не первый случайный посетитель**: доступ выдаётся только Telegram ID из `SUPER_ADMIN_TELEGRAM_ID`, когда allowlist пуст.
- Роль и статус пользователя перечитываются из базы на каждом запросе (`app/api/context.ts`): отзыв доступа действует для последующих запросов без ожидания окончания JWT.
- До production-развёртывания нужны исправления, перечисленные ниже. Оценка концепции: **8/10**; текущей готовности к публичному production: **4/10** (качественная оценка по исходникам, не результат пентеста).

## Блокеры P0 — исправить прежде всего

### P0.1. Telegram-админы не могут загружать изображения

**Файл:** `app/api/boot.ts`, маршрут `POST /api/upload` (около строк 76–108).

Маршрут использует `verifyLocalSessionToken`, затем `findLocalUserById`. Подлинные Telegram-сессии не проходят эту проверку. Кроме того, разрешён клиентский MIME `image/*`, включая SVG, а расширение определяется из ненадёжного имени файла; это опасно при раздаче файлов на том же origin.

**Задача:** проверять текущую сессию и роль `admin`/`super_admin` централизованно; запретить загрузки недоверенных форматов (SVG и исполняемых файлов); проверять сигнатуру и фактический формат, перекодировать в JPEG/PNG/WebP; применять безопасные имена и лимиты; вынести файлы из перезаписываемого `dist/`; добавить в `admin/src/pages/Products.tsx` реальную кнопку/компонент загрузки вместо ручной ссылки. Проверить `Content.tsx` и `Collections.tsx`.

**Приёмка:** Telegram admin и super_admin загружают допустимое изображение; посторонний и отозванный ID получают 401/403; SVG и подменённые файлы отклоняются; изображение сохраняется после нового деплоя.

### P0.2. Подмена заказа и перегрузка публичного API

**Файлы:** `app/api/orders-router.ts` (`orders.create`), `app/api/queries/orders.ts`, `app/src/pages/Home.tsx`.

Публичный метод принимает от клиента `items[].price`, `items[].name` и `total` как готовые данные. Можно передать несоответствующие цены и суммы, а также создавать фиктивные заказы. При этом витрина сейчас НЕ вызывает `orders.create`: корзина предлагает написать в мессенджер, поэтому раздел «Заказы» может оставаться пустым.

**Задача:** решить, нужен ли полноценный checkout. Если да — сервер принимает только ID товаров, количество и контактные данные; берёт актуальные цены/названия из БД, пересчитывает сумму, проверяет активность товаров, валидирует размеры и значения, лимитирует публичные запросы; добавляет форму оформления и уведомления. Если нет — отключить публичный `orders.create` и не имитировать работу заказов.

**Приёмка:** подмена клиентской цены не влияет на расчёт; мусорные ID/количества отклоняются; новый реальный заказ отображается в панели.

### P0.3. Dev-вход нельзя допустить на публичный сервер

**Файлы:** `app/api/telegram-auth-router.ts`, `app/api/router.ts`, `app/api/local-auth-router.ts`, `app/api/lib/env.ts`.

`auth.telegram.devLogin` доступен при `NODE_ENV != production && DB_DIALECT=sqlite`; `auth.local` с тестовым администратором аналогично. Это приемлемо только в изолированной локальной среде. README ошибочно утверждает, что `devLogin` в production не смонтирован: на деле процедура присутствует, но блокируется middleware.

**Задача:** исключить dev-процедуры из production router целиком; запретить работу небезопасного режима вне loopback/изолированного тестового контура; убрать стандартный `admin/123456` из нормального сценария; настроить fail-closed проверку окружения при старте.

**Приёмка:** на боевом сервере нет вызываемых методов devLogin/localLogin; при ошибочной конфигурации запуск останавливается или доступ запрещён.

### P0.4. Защитить браузерные сессии и изменения состояния

**Файлы:** `app/api/local-auth-session.ts`, `app/contracts/constants.ts`, `app/api/lib/cookies.ts`, `app/api/boot.ts`, `app/api/middleware.ts`.

JWT выдаётся на 1 год; cookie вне localhost имеет `SameSite=None`. В коде не обнаружена общая строгая проверка `Origin` / CSRF-токена для изменяющих состояние запросов; `SameSite=None` при cookie-based auth увеличивает риск CSRF.

**Задача:** выбрать SameSite=Lax/Strict для однодоменного UI; Secure+HttpOnly в production без зависимости от подменяемого Host; короткие сессии с управляемой ротацией/ревокацией; Origin/CSRF-защита на mutation endpoints и upload, строгие настройки reverse proxy.

**Приёмка:** вредоносный cross-origin запрос не может изменить данные в панели; отзыв allowlist прекращает полномочия; сессии не бессрочные.

## P1 — исправить до публичного релиза

### P1.1. Политика владельца и первоначальное назначение

**Файлы:** `app/api/queries/admin-allowlist.ts`, `app/api/admin-allowlist-router.ts`, `app/api/telegram-auth-router.ts`.

Текущее поведение: настроенный Telegram ID получает super_admin, только если allowlist полностью пуст; super_admin может создать второго super_admin, который затем может отозвать права первоначального владельца. Проверка «последний суперадмин» выполняется раздельно от изменения и не атомарна.

**Задача:** первоначальную запись создавать административной командой/seed-миграцией в транзакции; исходного владельца пометить защищённым или определить правило передачи владения; делать операции по ролям транзакционно; обеспечить резервный путь восстановления, если база повреждена/владелец потерял аккаунт. Сохранять уникальность Telegram ID.

**Приёмка:** случайный первый посетитель никогда не получает роль, другой админ не может захватить владельца, при конкурирующих запросах всегда остаётся хотя бы один привилегированный администратор.

### P1.2. Не публиковать Telegram ID владельца

**Файлы:** `app/api/telegram-auth-router.ts`, `admin/src/pages/Login.tsx`, `admin/src/pages/Access.tsx`.

`widgetConfig` отдаёт `superAdminTelegramId` всем анонимным посетителям; фронтенд демонстрирует его в dev-сценариях. ID не является криптографическим секретом, но нет причин публиковать его.

**Задача:** исключить поле из публичного конфига и соответствующие подсказки, оставить только server-side использование. Валидировать Telegram ID как `safeInteger > 0` и `auth_date` в допустимом интервале прошлого и будущего; предусмотреть ограничение повторного использования auth-пейлоада.

### P1.3. Аудит прав и сообщения об отказе

**Файлы:** `app/api/admin-allowlist-router.ts`, `admin/src/pages/Access.tsx`, `admin/src/pages/Login.tsx`.

**Задача:** отдельная таблица `adminAuditLog` (время, исполнитель Telegram ID, цель, операция, роль до/после, итог); показывать понятное состояние «Доступ запрещён» при `FORBIDDEN`, без раскрытия списка админов; удобное подтверждение опасных действий. Обычный admin не должен видеть список разрешённых ID, super_admin должен видеть.

### P1.4. Очистка старого OAuth и конфигурации

**Файлы:** каталог старого OAuth, `app/api/boot.ts`, `app/api/lib/env.ts`, `app/.env.example`.

В коде остаётся старый OAuth callback и обязательные переменные переменные старого OAuth и APP_ID, хотя доступ в админку должен идти только через Telegram. Обе системы используют cookie cookie старого OAuth.

**Задача:** проверить реальную необходимость интеграции, удалить неиспользуемый OAuth и маршруты либо изолировать их от admin-auth; переименовать cookie (например, `factura_admin_sid`) с согласованным session management; валидировать обязательные переменные, длину секрета и конфигурацию на старте.

### P1.5. Безопасность логов и ошибок

**Файлы:** `app/api/boot.ts`, `app/api/lib/clientlog.ts`.

При ошибке в tRPC-обработчике API возвращает поле `detail` с текстом исключения. `/api/log` публичен и пишет лог с ограничением по числу строк, но может создавать шум и хранить поступившие от клиента данные.

**Задача:** не возвращать внутренние exception details в production; ограничить/отключить клиентское логирование в production, использовать централизованный логгер и маскирование персональных данных.

8. Добавить индексы/внешние ключи и проверку связности товаров с коллекциями, где это уместно; удалить устаревшие файлы и зависимости после подтверждения их неиспользования.

## Авторизация: целевое поведение

1. Владелец задаёт `SUPER_ADMIN_TELEGRAM_ID` на сервере до первого входа. Не «первый зашедший становится главным».
2. Пользователь открывает `/admin/` и подтверждает Telegram Login/OIDC.
3. Бэкенд проверяет подпись, время, источник, наличие активного ID в allowlist и роль.
4. Неизвестный/отключённый ID получает `FORBIDDEN` и страницу «Доступ запрещён».
5. `admin` может управлять каталогом/контентом/заказами, но не списком допуска.
6. `super_admin` может добавлять/блокировать `admin`, просматривать аудит; передача полномочий владельца — отдельная защищённая операция.
7. Сессии выпускаются с коротким сроком, отзыв действует немедленно на сервере; операции изменения состояния защищены от CSRF.

## Обязательные автотесты

- Подпись Telegram: валидная, испорченная, протухшая, с временем в будущем, неправильный бот.
- Bootstrap владельца: совпадение с env, несовпадение, непустой allowlist, конкурентный вход, повторный запуск.
- Чужой ID: `FORBIDDEN`; активный admin: доступ к товарам, запрет allowlist; super_admin: разрешено управление доступом.
- Отозванный ID: существующая JWT-сессия сразу лишается прав.
- Параллельные запросы на понижение/удаление не могут оставить ноль суперадминов.
- Cookie-based CSRF: cross-origin mutation/upload отклоняются.
- Upload: Telegram admin может загружать JPEG/PNG/WebP, случайный клиент — нет, SVG и подменённые байты — запрещены.
- Orders: клиентская сумма игнорируется, итог считается сервером; спам/некорректный заказ ограничены.
- Production: dev endpoints отсутствуют или гарантированно недоступны; ошибки не раскрывают внутренние детали.
- CI: storefront + admin + API собираются и работают на новой БД; миграции применяются без ручных DROP TABLE.

## Примечание по Telegram

На ноябрь 2026 Telegram описывает новый Login/OIDC и маркирует старый iframe-виджет как legacy. Существующий `telegram-login.js` + HMAC может использоваться только по соответствующей старой схеме. При переходе на OIDC нужно реализовать полноценную проверку нового протокола; алгоритм проверки `Telegram.WebApp.initData` для Mini Apps другой, механизмы нельзя смешивать.

Документация:

- https://core.telegram.org/bots/telegram-login
- https://core.telegram.org/widgets/login-legacy
- https://core.telegram.org/bots/webapps
